## 設計判断と理由

### 1. 配置とモジュール構成

PC側の解析コードを `my_ak45/Mujoco/identification/` に新設した。ディレクトリ名を `sysid/` に
**しなかった**のは、`sys.path` に載った場合に名前空間パッケージとして `sysid` が解決され、
`from mujoco import sysid` と紛らわしくなるため。`data_collection/` と同じくフラットな
スクリプト構成とし、パッケージ化はしていない。

`data_collection/sysid_run_check.py` は起動過渡の判定ロジックを `check_run()` の中に
インラインで持っており公開関数として取り出せない。**Pi側のスクリプトは実験直後のホットパスで
動くため触らない**方針とし、判定ルール（`|vel| > 0.70*5.45` の最終サンプルが記録の前半1割に
収まっていれば50ms単位で切り上げ）を `csv_adapter.startup_trim_time()` に移植して相互参照の
コメントを残した。リファクタリングして共有する案も検討したが、Pi側の実験フローに影響する
変更を解析コードの都合で入れるのは割に合わないと判断した。

### 2. 実測列のずらし量を2に決定（食い違って見えた指示の整理）

`exp_005_sysid_excitation.py:202` は「実測列を1行前に詰める」、`sysid_run_check.py` の出力は
「3行前に詰める」と、リポジトリ内に異なる指示が存在していた。調べた結果、これらは矛盾ではなく
**別々の量を指していた**ことが分かったので、成分に分解して整理した:

| 数字 | 出どころ | 何を指すか |
|---|---|---|
| 1行 | `exp_005_sysid_excitation.py` | 記録の帳簿上のずれ。`update()` が「状態を読む→`_send_command()`」の順（`mit_can.py` の `update()` 末尾）なので、CSV行kの実測値は行kの指令を送る*前*の状態 |
| 約1.9行 | `sysid_run_check.py` の周波数応答 `L=1.82〜1.87ms` | 電流ループの物理的なむだ時間。1kHzなので約2サンプル |
| 3行 | `sysid_run_check.py` の相互相関ピーク | 上2つの合計（≈2.9）。1ms刻みの粗い測定で、一次遅れ T≈1.25ms の寄与も混じるためやや過大に出る |

MuJoCo の `rollout` は `sensor[i] = ctrl[0..i-1] への応答` という、実機のロギング規約
（＝1行目）と**まったく同じ**規約を持つ。したがって帳簿上の1サンプルは rollout 側が自動的に
合わせてくれるので、**補正すべきなのは物理的なむだ時間だけ＝約2サンプル**になる。

実際に `shift` を振ると最終コストは shift=0:0.665 / 1:0.408 / **2:0.334** / 3:0.344 となり
2で最小。独立に測定された L=1.82〜1.87ms（≈2サンプル）と直接一致しており、この値は
「3−1」という引き算の産物ではなく物理的なむだ時間そのものと解釈できる。
既定値を `DEFAULT_SHIFT = 2` とした。

なお `armature` はこの選択にほぼ影響されない（0.0128〜0.0123、約4%）のに対し、
`frictionloss` は 0.119〜0.179 と50%動く。摩擦を語る際はこの感度に注意が必要。

**ドキュメントの相互参照**: 「1行」「3行」だけを読んだ人が誤って二重補正しないよう、
`exp_005_sysid_excitation.py` のコメントと `sysid_run_check.py` の出力メッセージにも
この分解と `identify.py` の `DEFAULT_SHIFT` への参照を追記した（Pi側スクリプトの変更は
コメント・表示文字列のみで、判定ロジックには手を入れていない）。

### 3. MuJoCoへの入力は指令トルク（`.ai/logs/2026-08-13_01_*` の未決事項を決着）

電流ループの定常ゲイン K=0.817 の扱いとして「(a) 実測トルクを入力にする / (b) 遅れをモデル化する」
の選択が保留されていた。同条件で両方を実行して比較した結果、**指令トルク（`desired_torque`）を
採用**した:

- 実測トルク入力の方がフィットが明確に悪い（ステージ2でコスト 0.334 vs 0.938、2.8倍）。
  `desired_torque` は解析的に生成された滑らかな multi-sine であるのに対し、`output_torque` は
  電流計測から換算されたノイズを含む信号であり、開ループ積分で誤差が増幅されるためと考えられる
- `armature` の比は 0.770 で理論予測 K=0.817 とおおむね一致し、「指令トルク入力では armature が
  1/K 倍に膨らむ」という解釈は裏付けられた（ただし `frictionloss` の比は 1.257 と逆向きで、
  単純な比例関係では説明できない）
- 参照手法（`docs_syid/Mujoco_システム識別…について.md`）・`exp_005_sysid_excitation.py` の
  設計意図・フェーズ4の閉ループvalidation（制御器が出すのは指令トルク）のいずれとも整合する

**トレードオフ**: 得られる `armature`=0.0128 は真の反射慣性より約1.22倍過大である。
モデルとしては自己整合しており、同じ `Kt_actual` を使う制御コードをシミュレートする用途では
問題ないが、物理量として引用することはできない。

### 4. 段階的同定と、XMLのベースラインを0に揃えた理由

作業手順書 項目13/16 に従い armature → +frictionloss → +damping の3段階とした。
そのステージで対象にしないパラメータはXMLの値が固定値として効くため、各ステージが効果を
1つずつ足す形になるよう `models/ak45_36_joint.xml` の `damping` を 0.05 → 0.0 に変更した
（`frictionloss` は元から0）。

**`sysid.Parameter(frozen=True)` は使っていない**。`apply_param_modifiers` は frozen の
modifier をスキップするため、値を固定する用途には使えず（最適化ベクトルから外れるだけ）、
固定値はXML側に持たせるのが正しい。この挙動はドキュメントからは読み取れず、実装を読んで確認した。

### 5. `results/` の `report.html` を追跡対象外にした

`sysid.default_report()` が生成するHTMLは1ファイル約750KBで、3ステージ分で2.3MBになる。
`identify.py` と `data/raw/` のCSVから完全に再生成できるため `.gitignore` で除外し、
同定結果そのもの（`params.yaml` / `summary.txt`、いずれも数百バイト）だけを追跡することにした。
作業手順書の「未確定事項」に既に `data/raw/` のリポジトリサイズ懸念があることも考慮した。

## 未対応・既知の課題

- **`frictionloss` と `damping` は部分的に識別不能**。ステージ3で `damping` を足すと
  `frictionloss` が 0.160 → 0.098 に大きく動く一方、コスト改善は1.5倍程度にとどまる。
  どちらの値を採るかはフェーズ4で別軌道に対する再現性を見て決める必要がある。
  参照手法（RS02）も「有意な粘性摩擦は見えない」としており、`damping` は不要かもしれない。
  `armature` はこの影響をほぼ受けない（0.0125→0.0128、2%）。
- **K=0.817 の物理的原因は依然未特定**（`.ai/logs/2026-08-13_01_*` から継続）。現状は
  `armature` に吸収させており、その分 `armature` は物理的な反射慣性として使えない。
- MuJoCo側でむだ時間 L=1.87ms・一次遅れ T=1.24ms をモデル化する案（アクチュエータの
  `dyntype="filter"` 等）は検討していない。今回は `shift` による離散的な補正で済ませている。
- `models/ak45_36_joint.xml` の `inertial diaginertia=1e-5` は関節軸まわりの慣性に加算される
  ため、同定された `armature` は厳密には「全慣性 − 1e-5」（約0.1%）。XMLにコメントを残したが
  値自体は変更していない。
- 同定結果をXMLに反映する作業（フェーズ5 項目20）は未実施。フェーズ4のvalidationで
  `frictionloss`/`damping` の扱いが決まってからにすべきと判断した。
- 区間長は0.5s/1.0sしか試していない。作業手順書の分析では0.5sで可動範囲比4.5%の
  再現不能ずれが残る計算であり、さらに短くする余地はあるが未検証。
