## 設計判断と理由

### 背景: CSVの `t` 列は実時刻ではない

`sysid_run_check.py` が出力していた「(注): t列は公称時刻のため実ジッタは評価不可」という
注記の意味を確認する過程で、`SoftRealtimeLoop`（NeuroLocoMiddleware）の実装を読み、
`for t in loop:` が返す `t` は

```python
self.t1 += self.dt
...
return self.t1 - self.t0
```

という、`dt` を機械的に足しているだけの**予定時刻**であることを確認した。実際にその
タイミングで通信が完了したかとは無関係で、常に綺麗に1msずつ増える。これが
「CSVの `t` 列の差分の標準偏差が0.000ms」という不自然な観測の正体であり、
ジッタが皆無だったのではなく**記録の仕組み上ジッタが載る余地がなかった**。

一方 `SoftRealtimeLoop` は内部で真の誤差 `error = time.time() - self.ttarg` を集計して
おり、`report=True` なら `__del__()` でレポートを印字する。しかし `exp_005` は
`if t >= DURATION: break` でループを抜けるため、レポートが出ないまま終わっていた
（`config.yaml` で `report: true` にしているのに出力がない、という以前からの疑問の原因）。

### 1. タイミングレポートを console.log に記録させる（del loop）

- **採用した対応**: ループ終了直後に `del loop` を追加した。
- **検討の経緯**: 当初「ループを `break` で抜けずに正規のイテレーション終了で抜ける」案を
  検討したが、`SoftRealtimeLoop.__next__()` を読むと**キルシグナル以外で `StopIteration` を
  送出しない設計**であり、`break` が唯一の正常終了経路であることが分かった。したがって
  `break` 自体は変更できない。問題は「レポートが `loop.__del__()` でしか出力されず、
  `loop` はスクリプト末尾までグローバル参照が残るため、GCされるのが `console_log` が
  stdout/stderr を復元した後（インタプリタ終了時）になり、`console.log` に記録されないまま
  失われる」ことだったため、`console_log` のTeeが有効なうちに明示的に破棄する形にした。
  `del` で `__del__` が即座に発火することは、同じパターンの最小スクリプトで
  出力順序を確認して実証した。
- **実機での結果**: `console.log` に以下が記録されるようになった。
  ```
  In 10250 cycles at 1000.00 Hz:
      avg error: 0.000 milliseconds
      stddev error: 0.028 milliseconds
      percent of time sleeping: 86.9 %
  ```
  **1kHz制御がRaspberry Pi上で問題なく成立していることが初めて実測で確認できた**
  （これまで `config.yaml` の `dt` には「本リポジトリでの実機検証実績なし」と
  注記していた）。sleep時間が86.9%あり、CPUに余裕があるため `dt` を緩める必要はない。

### 2. CSVに wall_time 列を追加

`SoftRealtimeLoop` のレポートは全区間の集計値のみで、**どの時刻に遅れが集中したかが
分からない**。sysid では入力と出力の時間対応がそのまま同定誤差になるため、サンプル単位で
実時刻を残す必要があると判断した。

- **採用した対応**: `ExcitationLogger` のヘッダに `wall_time` 列を追加し、
  `motor.update()` 完了直後（＝そのイテレーションのCAN送受信が終わった瞬間）の
  `time.time() - wall_t0` を記録するようにした。`t`（予定時刻）と `wall_time`（実時刻）の
  両方が手に入るため、差分からサンプルごとのジッタを事後評価できる。
- **記録位置の判断**: ループ先頭ではなく `motor.update()` の直後にした。ジッタの主因は
  CAN通信の完了待ちであり、通信が終わった時刻を記録するのが実際の印加タイミングに最も近い
  ため。
- **`sysid_run_check.py` 側の対応**: `wall_time` 列があれば連続サンプル間の実間隔と公称dtの
  差から平均・標準偏差・最大値・外れ値の個数を評価する項目を追加した。連続サンプル間の
  差分を見ることで、`wall_time` と `t` の基準点のずれ（一定オフセット）に影響されず
  揺らぎだけを取り出せる。しきい値は実測値（stddev 0.028ms）の約3倍を警告ラインとした
  （統計的根拠ではなく経験的な余裕）。**`wall_time` 列がない2026-08-13以前のCSVには
  自動でフォールバックし従来の注記を出す**ため、既にコミット済みの4ランに対しても
  そのまま実行できる。
- **最大値だけでなく個数も出す判断**: 最初は最大値のみ表示していたが、実機データで
  「最大1.404ms」が出た際に単発か多発かが判断できなかったため、外れ値の個数と割合も
  併記するようにした（実測では 1.0ms超が 4/10250 = 0.04%）。

### 3. 実機で判明したジッタの実態

`wall_time` 列により、集計レポート（stddev 0.028ms）では見えなかった単発スパイクを検出した。

```
t=6.5625s  実間隔 1.0481ms  ずれ +0.0481ms
t=6.5635s  実間隔 2.4037ms  ずれ +1.4037ms  ← スパイク
t=6.5645s  実間隔 0.1516ms  ずれ -0.8484ms  ← 詰めて補正
t=6.5655s  実間隔 0.4272ms  ずれ -0.5728ms
t=6.5665s  実間隔 0.9952ms  ずれ -0.0048ms  ← 通常に復帰
```

重要なのは**遅延が蓄積しない**こと（`wall_time - t` の乖離は開始0.219ms→終了0.051ms）。
`SoftRealtimeLoop` が絶対時刻を目標とするため、遅れた分を直後のサンプルで詰めて自己補正
している。規模も 1.0ms超が0.04%、0.5ms超が16サンプルと限定的。

- **sysid での対処方針**: 指令トルクは公称 `t` で計算され実際には `wall_time` の時点で
  印加されるため、フェーズ3で `sysid.TimeSeries` の時刻軸に `t` ではなく **`wall_time` を
  使えばこのずれは補正される**。この誘導を `sysid_run_check.py` の出力メッセージにも
  含めた（外れ値が検出された場合のみ表示）。

## 未対応・既知の課題

- ジッタのしきい値（`JITTER_STD_WARN_MS` 等）は実測1セットからの経験値であり、
  統計的根拠はない。特に `JITTER_MAX_WARN_MS = 1.0` は実測の単発スパイク（1.404ms）を
  拾ってWARNになる水準であり、毎回WARNが出て形骸化するようなら見直しが必要。
- 2.4msスパイクの原因（CAN再送、OSのスケジューリング、GC等）は特定していない。
  0.04%と稀で自己補正もされるため、今回は追跡しなかった。
- `wall_time` を時刻軸に使うデータ整形（フェーズ3）は方針決定のみで実装は未着手。
- 既にコミット済みの4ラン（`_1786554555`/`_1786554734`/`_1786559877`/`_1786560014`/
  `_1786564070`）には `wall_time` 列がないため、それらを sysid に使う場合はジッタを
  考慮できない。今後取り直すか、`wall_time` 付きの新しいラン
  （`_1786565198` は列なし、`_1786566023` は列あり）を優先して使うかは未決定。
- **温度が上昇傾向**: 初期のランでは64〜65℃だったが、連続実行により68℃まで上がっている
  （上限75℃まで7℃）。まだ `sysid_run_check.py` の判定はPASSだが、続けて取得する場合は
  間隔を空ける必要がある。
