# sysid励振の振幅を1.5→0.9Nmに低減、コマンド送信順序を修正してむだ時間1サンプル分を削減

## 冒頭メタ情報

- 日時: 2026-08-13（時刻未記録）
- 対象ファイル:
  - `my_ak45/control_mit_can/config.yaml`（`experiment.sysid_excitation.amplitude`）
  - `my_ak45/Mujoco/data_collection/exp_005_sysid_excitation.py`（制御ループの処理順序）
- 種別: バグ修正

## 設計判断と理由

`exp_005_sysid_excitation.py` の実機初回取得（2026-08-13、10秒×2ラン、
`my_ak45/Mujoco/data/raw/exp005_sysid_excitation_1786554555` および `_1786554734`）の
データを解析したところ、2つの独立した問題が判明した。両ランとも10000/10000サンプルを
完走し統計値もほぼ一致しており、取得機構自体は正常だった。

### 問題1: 励振振幅が大きすぎ、トルク-速度特性の飽和域に突入していた

ピーク速度が 5.11 rad/s に達し、CubeMars公式仕様の無負荷回転速度 5.45 rad/s
（52rpm@24V、出力軸側）の94%まで到達していた。速度別に「実測トルク/指令トルク」の
回帰勾配を評価すると:

| \|v\| 区間 | 回帰勾配 |
|---|---|
| 0–4 rad/s | 約 0.81（ほぼ一定） |
| 4–5 rad/s | 0.53 |
| 5–6 rad/s | 0.002（実質ゼロ） |

さらに `|指令|>0.5Nm` のサンプルの4.07%で指令と実測の符号が逆転しており、その平均速度は
4.75 rad/s（全体平均2.85）だった。一方、電流は最大0.555Aで定格2A・ピーク6.5Aに全く
届いておらず、**電流制限ではなく逆起電力による速度飽和**であることが確認できた。
これは参照手法（`docs_syid/Mujoco_システム識別…について.md` 2節）が
「振幅が大きすぎる → 速度が乗りすぎてトルク-速度特性に入り、同定が崩れる」と明示的に
警告している失敗モードそのものである。

- **採用した対応**: `amplitude` を 1.5 → 0.9 Nm に低減（理論最大瞬時トルク 2.85 → 1.71 Nm）。
  ピーク速度が 5.11 × 0.9/1.5 ≈ 3 rad/s 前後に収まり、飽和域から外れることを狙う。
- **却下案**: `base_freq` を上げる案（4.0 → 6.7Hz 程度）も速度を下げる効果はあるが、
  後述の通り低速域ですら電流ループの追従が0.81に留まっており、周波数を上げると
  追従がさらに悪化する可能性が高いため見送った。振幅側を先に調整する。

### 問題2: コマンド送信順序により、CSV上で指令列が実測列より1サンプル余計に先行していた

指令トルクと実測トルクの相互相関を取ると約4msの見かけの遅れがあった。これを
励振信号の既知の3高調波（4.0 / 13.6 / 29.6 Hz）での同期検波により周波数応答として
分解したところ、単一の遅れではなく次の3成分の合成だった:

| 成分 | 値 |
|---|---|
| 定常ゲイン K | 0.782（周波数によらない一定の不足） |
| 一次遅れ時定数 T | 3.50 ms |
| むだ時間 L | 1.10 ms |

このモデルは3高調波すべての振幅比・位相を再現できた（振幅比 実測0.800/0.751/0.640 に対し
モデル0.779/0.749/0.655、位相 実測7.3°/19.5°/48.0° に対しモデル6.6°/22.0°/44.8°）。

むだ時間1.10msがサンプリング周期1msとほぼ一致していたため原因を調査したところ、
`TMotorManager_mit_can.update()` は内部で「状態を読む → `_send_command()` でコマンドを送信」
の順に処理する一方、スクリプトのループが `update()` を先に呼んでから
`set_output_torque_newton_meters()` を呼んでいたため、**ある行に記録した指令トルクの
送信が次のイテレーションまで持ち越されていた**ことが分かった。

実測列をkサンプルずらして再フィットすると:

| k | K | T [ms] | L [ms] | 残差 |
|---|---|---|---|---|
| 0 | 0.784 | 3.55 | +1.05 | 0.0306 |
| 1 | 0.776 | 3.30 | +0.25 | 0.0507 |
| 2 | 0.764 | 2.85 | −0.40 | 0.0998 |
| 3 | 0.738 | 1.85 | −0.55 | 0.2744 |

k=1でむだ時間がほぼ消え、k=2では負（応答が指令に先行する＝因果律違反）になることから、
余分な先行は**ちょうど1サンプル分**と確定した。

- **採用した対応**: ループ内で `set_output_torque_newton_meters()` を `motor.update()` より
  前に移動した。これにより指令が同じイテレーション内で送信される。制御の応答性自体も
  1ms改善する（純粋な改善であり、副作用としての悪化はない）。
- **消せない残り分**: この修正後も、記録される実測値は「1つ前のイテレーションで送信した
  コマンド」への応答である。`update()` が状態を読んでからコマンドを送る以上、指令を出す前に
  その応答を測ることは原理的に不可能なため、残る1サンプル分はスクリプト側では解消できない。
  MuJoCo sysid 用のデータ整形時に実測列を1行前に詰めて補正する必要があり、その旨を
  コード内コメントに明記した。
- **却下案**: ループ内で「1つ前のコマンド」を保持して実測値と組にして記録する案も検討したが、
  時刻列 `t` と指令値の対応がずれて読み手が混乱するため見送った。ずれを解消せずに
  明示的に文書化し、sysid のデータ整形段階で補正する方針とした。

### 補足: コードの構造からの推論が実測と食い違った件

当初、`update()` の実装（状態読み取り → 送信）とループ順序から「2サンプル分ずれるはず」と
推論したが、実測は1サンプルだった。CANフレームの到着タイミングをループに対して計測して
いないため構造からの推論が粗く、実測値を採用した。

## 未対応・既知の課題

- **定常ゲイン K=0.78 の原因は未特定**。指令側 `set_output_torque_newton_meters()` と
  実測側 `get_output_torque_newton_meters()` は同じ `Kt_actual`・`GEAR_RATIO` を通るため
  （`mit_can.py:1026`, `mit_can.py:1158`）、既知の `Kt_actual` 誤り（実体は
  `foc_current_kp`、`.ai/logs/2026-08-05_03_*` 参照）はこの比では打ち消し合う。
  したがって単位換算の副作用ではなく、モーター内蔵の電流ループが指令値に対して
  定常的に約22%不足している実挙動と考えられるが、ファームウェア側の確認は行っていない。
- **一次遅れ T=3.5ms・定常ゲイン K=0.78 をMuJoCo側でどう扱うかは未決定**。MuJoCoの最小モデル
  （ヒンジ + モーターアクチュエータ + armature/frictionloss/damping）はこれらを持たないため、
  (a) 指令トルクではなく実測トルクを入力にする、(b) 遅れをモデル化する、のいずれかを
  フェーズ3で選ぶ必要がある。なお実測トルクを使う場合、その絶対スケールは `Kt_actual` の
  誤りの影響を直接受け、公式ノートブック4節の「gear と mass が識別不能」と同型の
  armature とのトレードオフを生む点に注意。
- **1kHzでの実ジッタは未検証**。CSVの `t` 列は `SoftRealtimeLoop` の公称時刻であり
  （標準偏差0.000ms）、実時刻ではない。また `report: true` にしているが、ループを `break` で
  抜けているため `SoftRealtimeLoop` のタイミングレポートは出力されていない。
- **振幅0.9Nmが適切かは未検証**。ピーク速度3 rad/s前後という見積もりは飽和域を含む
  データからの単純比例外挿であり、実機での再取得による確認が必要。低くしすぎると今度は
  「動きが小さすぎて摩擦が同定できない」（参照手法2節）side に振れる可能性がある。
- 既存の2ラン（`_1786554555`/`_1786554734`）は飽和域のデータのため sysid には使えないが、
  「トルク-速度特性に入るとどうなるか」の記録としては価値があるため、削除するかどうかは
  未決定（現時点では残してある）。
