# CAN_Manager.__new__() の can0 down/up直後に0.3秒の待機を追加（初回実行時の接続失敗対策）

## 冒頭メタ情報

- 日時: 2026-08-11（時刻未記録）
- 対象ファイル:
  - `src/TMotorCANControl/mit_can.py`（`CAN_Manager.__new__()`）
- 種別: バグ修正

## 設計判断と理由

`exp_003_multi_motor.py`（3台同時制御）を実行したところ、1回目の実行では
`motors = [stack.enter_context(m) for m in motor_managers]` の中でmotor1の
`__enter__()`が`RuntimeError: Device not connected: AK45-36  ID: 1`で失敗し、
同じコマンドをそのまま再実行（2回目）すると成功する、という再現性のある事象が
報告された。

`__enter__()`（`mit_can.py:691-708`）は`power_on()`→`_send_command()`の後、
`check_can_connection()`（同ファイル1227-1263行）で起動メッセージを10回送信し、
100ms待ってから10回分の応答を確認する形で接続を検証している。一方、CAN通信の
土台となる`CAN_Manager`はプロセスにつき1回だけ生成されるシングルトン
（`__new__`、331-365行）で、生成時に必ず

```python
os.system("sudo /sbin/ip link set can0 down")
os.system("sudo /sbin/ip link set can0 up type can bitrate 1000000")
cls._instance.bus = can.interface.Bus(channel="can0", bustype="socketcan")
```

を行っていたが、`ip link up`の直後から待機時間ゼロで`Bus`オブジェクトを作成し、
すぐに通信を開始していた。`ip link set up`のioctl自体は即座に返るが、SPI接続の
CANコントローラ（Waveshare 2-CH CAN HAT等でよく使われるMCP2515系）は、
ビットレートの再ネゴシエーションやエラーカウンタのリセットが完了するまでに
実機依存で数百ms程度かかることがある。`check_can_connection()`側の100ms待機は
通常時はこれを吸収できているが、`down`→`up`し直した直後（＝スクリプトの
1回目の実行時。2回目以降はモーター・コントローラ双方が既に通信可能な状態に
「温まっている」ため同じ100ms待機でも間に合う）は不十分になり得ることが、
今回の再現パターン（1回目失敗・2回目成功）と整合する。

- **採用した対応**: `ip link set can0 up`の直後、`Bus`オブジェクト作成前に
  `time.sleep(0.3)`を追加した。`check_can_connection()`側の100ms待機を単純に
  伸ばす案よりも、根本原因である「インターフェース起動直後の不安定な期間」に
  的を絞って対処できる（`check_can_connection()`自体は複数モーターの`__enter__()`
  ごとに毎回呼ばれるため、そちらを伸ばすと3台構成で待機時間が3倍に積み上がって
  しまう。インターフェース起動はプロセスにつき1回のみのため、ここに待機を
  追加する方が影響範囲が小さい）。
- 0.3秒という値は、100msの応答待機に対して十分な余裕（3倍）を持たせつつ、
  スクリプト起動のたびに毎回発生するオーバーヘッドとしては許容範囲という
  経験的な判断。値の根拠となる実機データ（このハードウェアでの安定化に
  実際何msかかるか）は取得していない。
- **却下案**: `check_can_connection()`の100ms待機自体を伸ばす案は上記の理由
  （複数モーター分の待機が線形に積み上がる）で採用しなかった。また
  `ip link set can0 down/up`の実行結果（戻り値）をチェックして待機時間を
  動的に決める案も検討したが、`os.system()`の戻り値だけでは実際の物理的な
  安定化完了を判定できないため見送った。

## 未対応・既知の課題

- 今回の修正は仮説に基づく対症療法であり、実機での「1回目失敗・2回目成功」の
  再現性・0.3秒待機で実際に解消するかどうかは、この変更を反映した上での
  実機再実行でユーザー側に確認してもらう必要がある。
- 0.3秒という具体的な値は経験的な見積もりであり、実際に必要な最小待機時間を
  実測（例えば0.1秒刻みで段階的に減らして失敗が再発する閾値を探る）した
  わけではない。今後、環境によってはさらに長い待機が必要になる可能性がある。
- `CAN_Manager.__new__()`はプロセスにつき1回しか実行されないため、この0.3秒は
  スクリプト起動ごとに一度だけ発生するオーバーヘップであり、制御ループの
  リアルタイム性（100Hz等）には影響しない。
