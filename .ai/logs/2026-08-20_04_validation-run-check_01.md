## 設計判断と理由

### 1. `sysid_run_check.py` の拡張ではなく別スクリプトにした

`.ai/logs/2026-08-20_02_*` で「exp_008/exp_009 は `sysid_run_check.py` の検証ロジックが
multi-sine開ループ励振の周波数応答解析等を前提としているためそのまま適用できない」として
自動検証を見送っていた。今回はその前提を項目ごとに洗い直し、**移植できる項目とできない項目に
分かれる**ことを確認したうえで、別スクリプトにした。

| `sysid_run_check.py` の項目 | 別軌道データへの移植 |
|---|---|
| 1. 取得の完全性・実ジッタ | ✅ そのまま（共通関数として切り出して共有） |
| 2. 速度飽和 / 8. 速度デコード健全性 / 11. 温度余裕 | ✅ 同じ基準・同じしきい値で流用 |
| 5. 飽和の原因判別（電流） | ✅ 趣旨を変えてトルク・電流の余裕チェックへ |
| 9. 起動過渡 / 10. 励振の十分性 | 🔶 判定ロジックを別軌道用に作り直し |
| 3. トルク線形性 / 4. 符号反転 / 6. 指令-実測の遅れ / 7. 周波数応答 | ❌ **原理的に不可**（閉ループには `desired_torque` 列が存在しない） |

4項目が原理的に落ちるうえ、代わりに入る4項目（追従品質・飛びつき過渡・検証区間数・
双方向カバレッジ）は励振データ側には意味がない。同一関数に両方を通すと
「どの列があるか」による分岐だらけになり、判定表の意味も曖昧になるため分離した。

**却下案（`check_run()` に `mode="trajectory"` を足す）**: 判定項目が半分入れ替わるので
`mode` 分岐が関数全体に散る。しきい値定数も別系統になり、片方を触ったときにもう片方へ
波及していないか読み取れなくなる。

### 2. 共有したのは「記録の健全性」だけ

`sysid_run_check.py` から切り出して共有したのは項目1（サンプル数・`wall_time` ジッタ）のみ。
ここは制御則にも励振波形にもサンプリング周波数にも依存しない（判定はすべて公称dtからの
相対量）うえ、しきい値の根拠が長いコメントとして書かれており、2箇所に分裂させると
片方が古くなる。`_Report` はモジュール外から使うことになったため `RunCheckReport` に改名した。

**exp_005 の出力が1文字も変わらないことを実測で確認**（`exp005_sysid_excitation_1786575616`
に対する出力を改名・切り出しの前後で diff して完全一致）。

### 3. 区間切り出し規則は「移植」した（import しなかった）

項目4「検証区間数」は、PC側の `validate_trajectory.py` が実際に何区間切り出せるかを
先回りして数えるもの。本来なら `identification/csv_adapter.py` の `segment_starts()` を
呼びたいが、同モジュールは `from mujoco import sysid` を含み、**mujoco の入らない
Raspberry Pi 環境からは import できない**。そのため規則を `_count_segments()` として
移植し、「規則を変える場合は両方を揃えること」を両側にコメントした
（`csv_adapter.VEL_PEAK_WARN` が `sysid_run_check.py` から移植されているのと同じ事情）。

### 4. しきい値は実測レンジの外側に置き、FAIL は「検証が成立しない」水準に限った

`sysid_run_check.py` の「実機データ2セットからの経験値」と同じ方針で、exp_009 の実機5試行を
先に測ってからその外側に置いた。

| 項目 | 実測レンジ | WARN | FAIL |
|---|---|---|---|
| 飛びつき整定時間 | 0.01〜0.16 s | 0.35 s | 0.5 s（PC側の切り捨て幅） |
| 追従誤差RMS / 振幅 | 4.3〜13.4 % | 25 % | 50 % |
| 検証区間数 | 5〜15 | < 5 | ≤ 2 |
| 双方向の均衡 | 0.69〜0.98 | < 0.50 | — |
| 実際の可動範囲 / 指令 | 0.84〜1.07 | < 0.80 | — |

FAIL を付けたのは「そのデータでは検証が成立しない」3項目（飛びつきがPC側の切り捨て幅を
超える／追従が破綻している／区間が2本以下）だけにした。良品を落とすと実機の再取得コストが
高く、判定の信頼が下がってチェック自体が無視されるようになるため。

### 5. トルク余裕だけは追従区間ではなく記録全体で見る

他の品質項目は先頭0.5秒（PC側が捨てる範囲）を除いて評価するが、トルク・速度の**安全**余裕は
記録全体で見ている。インピーダンス則はトルクをclampせず、ピークはほぼ必ず飛びつき区間に
出るため、追従区間だけを見ると一桁小さい値になり「余裕がある」と誤読する
（実測: 追従区間 0.33 Nm に対し飛びつき込み 3.10 Nm）。

### 6. 呼び出しは実行フォルダ単位にした

`check_validation_run(RUN_DIR)` が `trial_*/` サブフォルダの有無で exp_009 形式か
exp_008 形式かを自動判別する。exp_009 の条件（振幅・周期）はCSV本体になく `manifest.csv`
にしか無いため、**manifest を書いた後に呼ぶ**必要がある（exp_009 側にその旨コメント済み）。
manifest が無い exp_008 では `desired_pos` 列から振幅を復元する。
例外は `sysid_run_check` と同じく握りつぶし、取得済みデータを失敗扱いにしない。

## 未対応・既知の課題

- **飛びつき時の速度が安全上限に迫っている（新規発見）**。取得済み5試行のうち2試行で、
  飛びつきのピーク速度が `safety.max_velocity`（6.0 rad/s）の **83〜85%**（5.00/5.12 rad/s）に
  達していた。あと少しで `SafetyMonitor` の緊急停止に掛かり、exp_009 の設計上それ以降の
  試行が全部中止になるところだった。今回はこれをWARNとして検出するに留め、**発生源の対策
  （軌道の始点へランプで移動する、K・振幅の組み合わせ上限を設ける等）は入れていない**。
  対策は exp_008/exp_009 の制御ロジックそのものの変更になり、取得済みデータとの比較可能性に
  影響するため別途判断が要る。
- **`sysid_run_check.py` のような周波数領域の検証がない**。閉ループの三角波追従では
  励振スペクトルが定義できず、「同定データと十分に違う運動か」を定量化できていない。
  現状は周期の広がり（最大/最小比）という粗い代理指標だけ。
- **判定はデータ品質までで、検証結果そのものは見ない**。「このデータで検証したら
  ステージ3のRMSがいくつになるか」はMuJoCoが要るのでPC側（`validate_trajectory.py`）の
  仕事のまま。Pi 上では「PC側に渡す価値があるデータか」までしか分からない。
- しきい値の根拠は実機**1セット（5試行）**のみ。`sysid_run_check.py` のしきい値が
  「実機データ2セットからの経験値」とされているのと同様、データ蓄積に応じた見直しが要る。
- 単発実行時の `config.yaml` フォールバック値（`max_temp=75` 等）はコード内に直書きで、
  `config.yaml` を変えても追従しない。Pi 上では `load_config()` が通るので実害はない。
